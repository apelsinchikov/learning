# Документ дизайна курса (аналог GDD)

Курс: **«OpenAPI с нуля»** · интерактивный сайт https://apelsinchikov.github.io/learning/
Версия документа: 1.0 · Статус: действующий курс, 21 урок

Как читать: документ отвечает на вопросы «для кого», «чему учим», «как ученик
проходит путь» и «что делает курс приятным». Поведение сайта по пунктам — в
`openspec/specs/`. Планы развития — в `openspec/changes/`.

---

## 1. Видение

**Одним предложением.** Человек без программирования за вечер-два учится читать и
писать базовое описание API в формате OpenAPI и видит результат сразу, в
Swagger UI.

**Обещание ученику.** «Ты не будешь читать стены текста. Ты будешь писать сам,
сайт подскажет, где ошибка, а в конце у тебя будет собственная рабочая
спецификация».

**Чего курс не делает.** Не учит программировать, не учит проектировать
сложные системы и не покрывает расширенные возможности OpenAPI.

## 2. Аудитория

| Кто | Что умеет | Чего боится | Что хочет |
|---|---|---|---|
| Бизнес-пользователь, начинающий системный аналитик | Пользуется Excel, пишет ТЗ | «Код», «технические термины» | Понимать, о чём спорят разработчики, и описывать API сам |
| Тестировщик, менеджер продукта | Читает документацию | Сложные схемы | Читать готовые спецификации |
| Студент / переходящий в аналитику | Знает «что такое сайт» | Не знать с чего начать | Показать результат работодателю |

Допущение: ученик не знает HTTP, JSON и YAML. Всё объясняется по ходу.

## 3. Цели обучения

После курса ученик **умеет**:
1. Объяснить, что такое API, endpoint, OpenAPI и чем OpenAPI отличается от сервера.
2. Писать YAML с правильными отступами.
3. Описать адреса и методы (`paths`, `get/post/put/patch/delete`).
4. Описать параметры (`path`, `query`) и их ограничения.
5. Описать данные схемами (`type`, `properties`, `required`, `format`, ограничения).
6. Описать тело запроса и ответа (`requestBody`, `content`, `$ref`, `array`).
7. Выбирать коды ответов (200, 201, 204, 400, 404, 409, 500).
8. Назвать адреса и поля по общепринятым правилам.
9. Понимать, что модель API ≠ модель базы данных, и проектировать ответ из нескольких таблиц.

Измеримый итог: ученик самостоятельно проходит итоговую практику (урок 18)
и практику «из базы данных» (урок 20).

## 4. Принципы дизайна курса

1. **Маленькие шаги.** Один урок — одна идея. Практика сразу после теории.
2. **Руками, а не копированием.** Примеры в теории нельзя скопировать
   (сайт отвечает «Неа! Пиши сам!»). Печатая, человек запоминает.
3. **Бытовая аналогия перед термином.** API — меню в кафе, схема — анкета,
   `$ref` — ссылка в интернете, PUT/PATCH — анкета в отделе кадров.
4. **Один сквозной пример.** Users API: каждый урок достраивает его.
5. **Ошибка — часть обучения.** Проверка объясняет, что исправить, а не просто «неверно».
6. **Сразу видно результат.** После успешной проверки появляется настоящий
   Swagger UI, в котором можно нажать «Try it out».
7. **Без давления.** Вход необязателен, прогресс сохраняется, к любому
   уроку можно вернуться.

## 5. Тон и язык

- Русский, на «ты», короткие предложения, без сленга и без канцелярита.
- Термин вводится вместе с пояснением и примером.
- Эмодзи — только как иконки уроков.
- Тексты ошибок называют место и ожидаемое значение:
  «Для PUT /users/{id} укажи summary: Update user».
- Успех — тёплая, но краткая фраза: что получилось и что будет дальше.

## 6. Цикл ученика (core loop)

```
Открыть урок → прочитать теорию → «Следующий урок» (теория прочитана)
            → открыть практику → написать YAML → «Проверить»
            → ошибка? читать подсказку, исправлять
            → успех: Swagger UI + сообщение + галочка в сайдбаре + счётчик
            → следующий урок
```

**Награды:** галочка в сайдбаре, рост счётчика «N / M» и полосы в шапке,
рабочая документация в Swagger UI, итоговая собственная спецификация.

**Сохранность.** Гость: прогресс в браузере. Вошёл через Google или Яндекс:
прогресс переезжает между устройствами; черновик каждой практики сохраняется.

## 7. Карта курса

Тип: Т — теория, П — практика. «Результат» — что у ученика получилось.

| № | Тип | Урок | Новое | Результат |
|---|---|---|---|---|
| 1 | Т | Что такое API и OpenAPI | API, endpoint, OpenAPI, Swagger UI | Понимает, зачем нужно описание |
| 2 | Т | YAML и отступы | ключ: значение, вложенность, Tab/Shift+Tab | Умеет читать структуру по отступам |
| 3 | П | Заготовка описания | `openapi`, `info`, версии OpenAPI и API | Первые строки спецификации |
| 4 | П | Hello Users | `paths`, `get`, `summary`, `responses` | Первый endpoint `GET /users` |
| 5 | Т | Адреса, методы и названия | 5 методов, PUT vs PATCH, имена адресов, `summary`, `operationId`, коды | Правила названий |
| 6 | П | Describe Users API | второй метод у адреса | `POST /users` рядом с `GET` |
| 7 | Т | Схемы и свойства | `components/schemas`, `properties`, `required`, `format`, ограничения | Читает схему |
| 8 | П | Схема User | собственная схема | Схема `User` |
| 9 | Т | Запрос, ответ и JSON | `requestBody`, `content`, `$ref`, JSON | Связывает схему и операцию |
| 10 | П | Create User | `requestBody` + `$ref` | Создание пользователя описано |
| 11 | Т | Списки | `array`, `items` | Отличает объект и список |
| 12 | П | Список пользователей | ответ — массив `User` | `GET /users` возвращает список |
| 13 | Т | Параметры | `path`, `query`, `required` | Различает виды параметров |
| 14 | П | Get User | `/users/{id}` | Получение по номеру, 200 и 404 |
| 15 | П | Search and filtering | `limit`, `offset`, `search` | Параметры списка |
| 16 | Т | Коды ответов и ошибки | 2xx/4xx/5xx, несколько ответов | Выбирает код |
| 17 | П | Update and Delete | PUT/DELETE (+ PUT vs PATCH в теории) | Изменение и удаление |
| 18 | П | Final Users API | сборка всего | Полная спецификация (**итог 1**) |
| 19 | Т | Из базы данных в API-модель | таблицы, PK/FK, 1:N, JOIN, DTO, Database Model ≠ API Model | Понимает, откуда берутся данные |
| 20 | П | Users API из базы данных | вложенные массивы телефонов/адресов/устройств | Спроектированный ответ (**итог 2**) |
| 21 | Т | Best practices | сводка правил и чек-лист | Памятка для будущей работы |

**Кривая сложности:** уроки 1–4 — вход (лёгкие), 5–12 — основное содержание
(средние), 13–18 — закрепление и сборка, 19–20 — пик (проектирование из базы),
21 — выдох и памятка.

## 8. Сквозной пример

**Users API** (уроки 1–18): `GET/POST /users`, `GET/PUT/PATCH/DELETE /users/{id}`.
Модель `User`: `id`, `name`, `email`.

**Расширенная модель** (уроки 19–20): `firstName`, `lastName`, `phones[]`,
`address[]`, `devices[]`. Сделана отдельным примером, чтобы показать
разницу между базой и API.

Мок-данные для «Try it out» лежат в `src/mock/mockApi.js`.

## 9. Устройство урока

**Теория.** Вступление → определения → аналогии → код с разбором «по строкам» →
предупреждения о типичных ошибках → «Главное из урока».

**Практика.** Описание задачи (что добавить, какие значения указать) →
стартовый YAML → редактор → «Проверить» → результат.

Формат данных урока и допустимые типы секций описаны в
`openspec/specs/course-content/spec.md`.

## 10. Интерфейс (UX)

- **Шапка:** название, счётчик прогресса, вход/имя.
- **Сайдбар:** список уроков, подсветка текущего, галочки.
- **Теория:** одна колонка, крупные заголовки, выделенные блоки
  (определение, важно, предупреждение).
- **Практика:** слева задача, справа редактор и результат; кнопка «Проверить»
  всегда на виду.
- **Редактор:** тёмная тема, подсветка YAML, автоотступы, Tab/Shift+Tab.
- **Мобильная версия:** блоки перестраиваются в колонку, без горизонтальной
  прокрутки.
- **Подвал:** ссылка на политику конфиденциальности.

## 11. Обратная связь ученику

| Ситуация | Что видит ученик |
|---|---|
| YAML сломан | Ошибка синтаксиса |
| Пустой `paths` | Понятное объяснение |
| Нарушены правила OpenAPI | Ошибка парсера |
| Не выполнено условие задачи | «Для POST /users укажи summary: Create user» |
| Всё верно | Swagger UI + поздравление + галочка |

## 12. Принципы написания новых уроков

1. Один урок — одна идея; больше двух новых терминов подряд не вводить.
2. Начать с вопроса «зачем это нужно», потом «как».
3. Аналогия из повседневной жизни, потом формальное определение.
4. Пример кода — короткий (до ~15 строк) и разбор «строка за строкой».
5. Предупреждение о самой частой ошибке новичка.
6. В конце — 1–3 тезиса «Главное из урока».
7. Практика берёт только то, что уже объяснено; ожидаемые значения прописаны в задаче.
8. Не вводим продвинутое: `x-*`-расширения, `callbacks`, `webhooks`, `oneOf/allOf`.
9. Названия в примерах — английские, `camelCase` для полей и `operationId`.
10. Новый урок получает уникальный `id`; прогресс опирается на `id`, а не на номер.

## 13. Вход и данные

- Вход необязателен. Способы: Google, Яндекс (OAuth).
- Сохраняется: прочитанное, решённое, текущий урок, черновики.
- Политика конфиденциальности: `public/privacy.html`.
- Подробнее: `openspec/specs/authentication/`, `progress-saving/`, `privacy-and-legal/`.

## 15. Известные пробелы

См. ревью и дорожную карту:
- нет практики на ошибки 400/409 (→ `add-error-responses`);
- PATCH объяснён, но не отработан (→ `add-patch-practice`);
- нет `enum` и `default` (→ `add-enum-and-defaults`);
- несоответствия в уроках 19–21 и отсутствие определений HTTP/REST
  (→ `fix-course-consistency`);
- поле `theoryLinks` в практиках не показывается в интерфейсе.

## 16. Дорожная карта

**Приоритет 1.** Ошибки (урок + практика), практика PATCH, `enum`/`default`,
`components/parameters`.
**Приоритет 2.** HTTP/REST/Swagger-определения, `servers` и `tags`, практика
«прочитай чужую спецификацию», практика «найди ошибку», «из JSON в схему»,
вложенные ресурсы, формат ответа со списком и пагинацией.
**Приоритет 3.** Урок про безопасность на уровне понимания, второй итоговый
проект по ТЗ, мини-тесты, словарик, страница «Что дальше».

## 17. Риски

| Риск | Что делаем |
|---|---|
| Новичок бросает на отступах YAML | Урок 2, автоотступы, понятные подсказки |
| Строгая проверка раздражает | В задаче явно написаны нужные значения; смягчать правила там, где допустимы варианты |
| Курс «растёт» вширь и теряет простоту | Держать границы (раздел 12, пункт 8); новое — только через OpenSpec-предложение |
| Расхождение уроков и проверки при правках | Менять урок, проверку и тест вместе |
| Зависимость от сторонних входов | Вход необязателен, курс работает без него |

## 18. Глоссарий

- **API** — способ, которым одна программа просит что-то у другой.
- **Endpoint** — одно действие в API: адрес + метод.
- **OpenAPI** — правила записи описания API в виде текста.
- **Swagger UI** — страница, показывающая описание и позволяющая пробовать запросы.
- **YAML** — формат записи данных отступами.
- **Schema (схема)** — описание того, из чего состоят данные.
- **`$ref`** — ссылка на готовую часть описания.
- **DTO** — объект, подготовленный для передачи данных между системами.
- **Database Model / API Model** — как данные хранятся в базе и как отдаются клиенту.
